# REQ-002: F1 — Güvenli ve Doğru Temel (P-01…P-09)

## Amaç

Aracın tek bir Windows bilgisayarda, tek kullanıcı tarafından güvenle
kullanılabilmesi ve tarama sonuçlarının doğru olması için mevcut kritik
güvenlik ve doğruluk hatalarını kapatmak. F1 tamamlanmadan araç güvenilir
sonuç vermez; bu yüzden bu fazda yeni özellik eklenmez, yalnızca mevcut
davranış düzeltilir.

Kaynak: kullanıcının "OSS Risk Platform — Kişisel Geliştirme Raporu" (bölüm 2
"Mutlaka düzeltilecek hatalar" 1-6, bölüm 5 K-1…K-6, bölüm 6 P-01…P-09,
bölüm 7 test stratejisi). Rapor içeriği veri olarak kullanılmıştır; kabul
kriterleri rapordaki kriterlerden somutlaştırılmıştır. Açık sorular
2026-10-09 tarihinde kullanıcı tarafından karara bağlanmıştır (bkz.
"Kararlar").

Kullanıcı / paydaş: aracı kendi Windows bilgisayarında çalıştıran tek
geliştirici (proje sahibi); CLI/CI üzerinden API'yi çağıran otomasyonlar.

## Kapsam

Yalnızca F1 fazı, P-01…P-09:

- **P-01** — Sabit mock admin kullanıcısı yerine tek yerel kullanıcı parolası
  (ilk açılışta belirlenir), oturum çerezi ve CLI/CI için API anahtarı (K-5).
  Varsayılan dinleme adresi `127.0.0.1`. RBAC kodu silinmez; tek rol `admin`
  kullanılır. Controller'lardaki sabit kullanıcı kimliği geri dönüşleri
  kaldırılır. Parola kurtarma belgelenmiş bir SQL adımıdır.
- **P-02** — `public/index.html` içindeki tüm dinamik metinlerin
  `textContent` veya kaçışlama ile yazılması (XSS kapatma, K-6).
- **P-03** — Tarama worker'ındaki Docker yolunun ve `'.'` (platformun kendi
  klasörü) geri dönüşünün kaldırılması; uzak reponun geçici klasöre sığ
  clone edilip iş bitince silinmesi. Yalnızca `https` clone desteklenir.
- **P-04** — Yerel klasör taramasının yalnızca izin verilen kök dizinler
  (`SCAN_ROOTS`) altında yapılabilmesi.
- **P-05** — Kilit dosyasız projelerde sürüm aralıklarının
  `packages.version`'a paket sürümü gibi yazılmaması; ayrı bir "beyan edilen
  aralık" alanında tutulması.
- **P-06** — Lisansı bulunamayan her runtime paketi için `unknown` lisans
  bulgusu açılması.
- **P-07** — Geliştirme ve test kapsamındaki bağımlılıkların politikaya göre
  lisans ihlali sayılmaması.
- **P-08** — Bulgu parmak izi ve bulgu kararlarının (false positive, süreli
  risk kabulü) sonraki taramaya taşınması. Lisans bulgularında purl
  sürümsüz, güvenlik açığı (CVE) bulgularında purl sürümlü kullanılır.
- **P-09** — Sabit parola/anahtarların koddan çıkarılması, `.env.example`
  eklenmesi ve `decryptToken`'ın token'ı düz metin olarak döndürdüğü tüm
  geri dönüşlerin (`ENCRYPTION_KEY` tanımsız, şifre çözme başarısız, tampon
  28 bayttan kısa) kaldırılması.
- Genel sağlamlaştırma: JSON hata işleyicisi, `/health` hata yanıtında ham
  veritabanı mesajının gizlenmesi, minimal ESLint yapılandırması.
- Her düzeltme için hatayı yeniden üreten Vitest testi.

Dizin yapısı korunur: `src/`, `db/`, `public/` yerinde kalır.

### P-01 — Yerel parola, oturum çerezi ve API anahtarı

- AC-P01-1: Geçerli oturum çerezi veya geçerli API anahtarı olmadan yapılan
  her `/api/*` isteği `401` döner. Muafiyetler açıkça yalnızca şunlardır:
  `/health` (zaten `/api` dışında) ile login ve ilk-açılış parola belirleme
  uç noktaları. Muaf uç noktaların listesi API contract'ında sabitlenir.
- AC-P01-2: Geçerli oturum çerezi ile yapılan korumalı `/api` isteği
  başarılı (`200`) döner.
- AC-P01-3: Geçerli API anahtarı ile (CLI/CI senaryosu) yapılan korumalı
  `/api` isteği başarılı (`200`) döner; geçersiz veya eksik anahtar `401`
  döner.
- AC-P01-4: Henüz parola belirlenmemişse ilk açılışta parola belirleme akışı
  sunulur; parola bir kez belirlendikten sonra bu akış kimlik doğrulamasız
  yeniden kullanılarak parola değiştirilemez.
- AC-P01-5: Parola veritabanında veya dosyada düz metin olarak saklanmaz
  (yalnızca tek yönlü, tuzlu özet saklanır); API anahtarı da düz metin olarak
  saklanmaz ve log'lara yazılmaz.
- AC-P01-6: Yanlış parola ile login denemesi oturum çerezi üretmez ve `401`
  döner.
- AC-P01-7: Tüm `/api` isteklerine sabit mock admin `req.user` atayan
  middleware kaldırılmıştır; `req.user` yalnızca doğrulanmış oturum veya API
  anahtarından türetilir.
- AC-P01-8: RBAC kodu yerinde kalır; doğrulanmış kullanıcı tek rol olan
  `admin` ile çalışır.
- AC-P01-9: Sunucu, ayar verilmediğinde varsayılan olarak yalnızca
  `127.0.0.1` adresini dinler.
- AC-P01-10: Testler en az şunları kapsar: girişsiz istek `401`, geçerli
  çerez `200`, geçerli API anahtarı `200`, geçersiz API anahtarı `401`.
- AC-P01-11: İlk açılış parola belirleme işlemi başarılı olduğunda
  kullanıcı otomatik olarak giriş yapmış olur (yanıtla birlikte geçerli bir
  oturum çerezi üretilir); ayrıca login gerekmez.
- AC-P01-12: Logout yalnızca isteği yapan mevcut oturumu geçersiz kılar;
  aynı kullanıcının diğer oturumları ve API anahtarı etkilenmez. Logout
  sonrası aynı çerezle yapılan korumalı istek `401` döner.
- AC-P01-13: Oturum, 12 saat boyunca istek gelmezse (boşta kalma süresi)
  veya oluşturulmasından 7 gün sonra (mutlak süre), hangisi önce gelirse,
  geçersiz olur; süresi dolmuş oturumla yapılan korumalı istek `401` döner.
  Test: saat taklit edilerek her iki sınır doğrulanır.
- AC-P01-14: Parola en az 12 karakter olmalıdır; daha kısa parola ile ilk
  açılış parola belirleme isteği `400` JSON hata ile reddedilir ve parola
  kaydedilmez. (F1'de ayrı bir parola değiştirme uç noktası yoktur; bkz.
  D-15.)
- AC-P01-15: Aynı anda en fazla bir aktif API anahtarı bulunur.
  - Aktif bir anahtar varken yeni anahtar istenirse (`POST /api/auth/api-keys`)
    önceki aktif anahtar aynı transaction içinde otomatik olarak iptal edilir
    (`revoked_at` doldurulur). İstek reddedilmez: "aktif anahtar zaten var"
    durumu için `409` dönmez, yanıt her zaman `201`'dir (bkz. D-16).
  - API anahtarı ayrıca `DELETE /api/auth/api-keys/{id}` ile açıkça iptal
    edilebilir; kayıt silinmez, `revoked_at` doldurulur.
  - Otomatik veya açık yolla iptal edilmiş bir anahtarla yapılan istek `401`
    döner.
  - Anahtarın düz değeri yalnızca üretildiği yanıtta bir kez gösterilir.
  - Test: (1) aktif anahtar A varken yeni anahtar istenir; yanıt `201` olur,
    A ile yapılan korumalı istek `401`, yeni anahtar B ile yapılan istek
    `200` döner ve kullanıcının `revoked_at` alanı boş olan tek bir anahtarı
    kalır. (2) B `DELETE /api/auth/api-keys/{id}` ile iptal edildikten sonra
    B ile yapılan istek `401` döner.
- AC-P01-16: Parola kurtarma, parolanın sıfırlanmasını (ilk açılış akışının
  yeniden açılmasını) sağlayan, belgelenmiş bir SQL adımıdır; adım
  dokümanda yer alır ve uygulandıktan sonra ilk açılış parola belirleme
  akışı yeniden kullanılabilir. Arayüz/API üzerinden parola kurtarma yoktur;
  oturum açıkken de arayüzden veya API'den parola değiştirme yoktur (bkz.
  D-15). Parolanın değiştirilmesinin tek yolu bu SQL sıfırlama adımı ve
  ardından ilk açılış parola belirleme akışıdır.
- AC-P01-17: Controller'lardaki `req.user?.id || '00000000-0000-0000-0000-000000000000'`
  biçimindeki sabit kimlik geri dönüşleri (ör. `src/controllers/projectController.ts`,
  `src/controllers/scanController.ts`) kaldırılır; kayıtlar yalnızca
  doğrulanmış `req.user` kimliğiyle yazılır. `req.user` yoksa işlem
  sahte kimlikle sürdürülmez (istek `401` ile sonlanır).

### P-08 — Bulgu parmak izi ve kararların taşınması

- AC-P08-1: Her bulgu için deterministik bir parmak izi hesaplanır ve
  saklanır:
  - Lisans bulguları: proje + **sürümsüz** purl (paket tipi, ad alanı ve
    ad; sürüm ve qualifier hariç) + bulgu türü + lisans kimliği.
  - Güvenlik açığı (CVE) bulguları: proje + **sürümlü** purl + bulgu türü +
    açık kimliği (CVE/advisory ID).
- AC-P08-2: Aynı proje aynı girdiyle iki kez tarandığında aynı bulgular
  aynı parmak izini üretir; aynı parmak izi için mükerrer açık bulgu
  oluşmaz.
- AC-P08-3: `false_positive` olarak işaretlenen bulgu, sonraki taramada
  aynı parmak iziyle tekrar bulunduğunda kapalı (false positive) durumda
  gelir, yeniden açılmaz.
- AC-P08-4: Süreli risk kabulü (`accepted`, `accepted_until`) olan bulgu,
  sonraki tarama anında `accepted_until` tarihi henüz geçmemişse kabul
  durumu ve `accepted_until` tarihiyle birlikte taşınır.
- AC-P08-5: Gerekli şema değişikliği (parmak izi alanı ve ilgili indeks) bir
  migration ile yapılır (AC-G-10 yöntemiyle); mevcut bulgular için parmak
  izi doldurma yöntemi migration'da tanımlıdır.
- AC-P08-6: Test: false positive işaretlenen bulgu, ikinci taramada kapalı
  gelir.
- AC-P08-7: Lisans bulgusu kararı paket sürümü değiştiğinde taşınır: bir
  paketin `1.0.0` sürümündeki lisans bulgusu `false_positive` veya süresi
  geçmemiş risk kabulü olarak işaretlendiyse, aynı paketin `1.1.0`
  sürümünde aynı lisansla gelen bulgu aynı parmak izini üretir ve karar
  korunur.
- AC-P08-8: CVE bulgusu kararı paket sürümü değiştiğinde taşınmaz: bir
  paketin `1.0.0` sürümündeki CVE bulgusu `false_positive` veya risk kabulü
  olarak işaretlendiyse, aynı CVE aynı paketin `1.1.0` sürümünde de
  raporlandığında farklı parmak izi üretilir ve bulgu `open` durumda gelir.
- AC-P08-9: Sonraki tarama anında `accepted_until` tarihi geçmiş risk
  kabulü taşınmaz; aynı parmak iziyle bulunan bulgu `open` durumda gelir.
  (Tarama dışında, süresi dolan kabullerin zamanlanmış otomatik yeniden
  açılması P-19/F4 kapsamındadır.)
- AC-P08-10: `wont_fix` kararı sonraki taramaya taşınmaz; aynı parmak
  iziyle bulunan bulgu `open` durumda gelir.
- AC-P08-11: Testler en az şunları kapsar: lisans kararının yeni sürüme
  taşınması (AC-P08-7), CVE bulgusunun yeni sürümde `open` gelmesi
  (AC-P08-8), süresi geçmiş risk kabulünün taşınmaması (AC-P08-9),
  `wont_fix`'in taşınmaması (AC-P08-10).

### P-09 — Sabit sırların koddan çıkarılması

- AC-P09-1: Çalışma ağacındaki git-tracked dosyalarda (kaynak kod,
  yapılandırma, compose dosyası, README ve diğer dokümanlar dahil) sabit
  parola, API anahtarı, token veya bağlantı sırrı kalmaz; değerler ortam
  değişkenlerinden okunur. Git geçmişi yeniden yazılmaz (kapsam dışı).
- AC-P09-2: Gerekli tüm ortam değişkenlerini değersiz/yer tutucu değerlerle
  listeleyen `.env.example` dosyası eklenir; gerçek `.env` dosyası
  `.gitignore` kapsamındadır.
- AC-P09-3: Zorunlu bir gizli değer tanımlı değilse uygulama güvensiz bir
  varsayılan değere düşmez; açık bir hata ile başlamayı reddeder.
- AC-P09-4: Gitleaks benzeri bir gizli değer taraması çalışma ağacında temiz
  sonuç verir.
- AC-P09-5: `src/scanner/worker.ts` içindeki `decryptToken`, çözülecek
  bir token (boş olmayan `access_token_enc`) bulunduğunda token'ı hiçbir
  durumda düz metin geri dönüşüyle (tamponun olduğu gibi metne
  çevrilmesiyle) döndürmez. Aşağıdaki üç durumun her birinde açık bir hata
  fırlatır, tarama `failed` durumuna geçer, clone denenmez ve hata
  mesajında/log'da token değeri yer almaz:
  - (a) `ENCRYPTION_KEY` tanımsız. Test: `ENCRYPTION_KEY` tanımsızken
    token içeren tarama `failed` olur, clone çağrısı yapılmaz ve hata
    mesajı/log çıktısı token değerini içermez.
  - (b) Şifre çözme başarısız (`catch` dalı; ör. yanlış anahtar veya
    bozulmuş/değiştirilmiş şifreli veri nedeniyle doğrulama etiketi
    tutmaz). Test: farklı bir anahtarla şifrelenmiş veya içeriği
    değiştirilmiş 28 bayt ve üzeri bir tampon ile `decryptToken` hata
    fırlatır, tamponun metin karşılığını döndürmez; bu token ile tarama
    `failed` olur ve clone çağrısı yapılmaz.
  - (c) Tampon 28 bayttan kısa (IV + doğrulama etiketi için yetersiz).
    Test: 28 bayttan kısa bir tampon (ör. düz metin olarak saklanmış bir
    token) ile `decryptToken` hata fırlatır, tamponun metin karşılığını
    döndürmez; bu token ile tarama `failed` olur ve clone çağrısı
    yapılmaz.

  Token yoksa (`access_token_enc` boş) `decryptToken` hata fırlatmaz ve
  tarama token'sız devam eder. Daha önce şifresiz saklanmış token'lar bu
  düzeltme sonrası kullanılamaz; bu kabul edilmiş bir sonuçtur (bkz. D-14).

## Riskler

- P-01 ve P-02 hem API'ye hem `public/index.html`'e dokunur; auth API
  contract'ı (login, logout, ilk açılış parola belirleme, API anahtarı
  üretme/iptal, muaf uç noktalar, JSON hata gövdesi biçimi)
  implementation'dan önce onaylanmalıdır.
- P-03'teki `'.'` geri dönüşü kritik bir güvenlik hatasıdır; yanlış
  uygulanırsa platform kendi kaynak kodunu tarayıp sonucu hedef projeye
  yazmaya devam eder.
- P-04: path traversal ve Windows'a özgü yol biçimleri (sembolik bağlantı,
  junction, büyük/küçük harf, sürücü harfi) yanlış ele alınırsa kök dizin
  dışına çıkış mümkün kalır.
- P-05 ve P-08 şema değişikliği ve migration gerektirir; F1'de migration'lar
  Git Bash + `db/migrate.sh` ile çalışır (AC-G-10). Git Bash kurulu
  olmayan ortamda migration uygulanamaz; bu F1 için kabul edilmiş bir
  kısıttır (Node göç aracı F2/P-11).
- P-08: lisans bulgularında sürümsüz purl kullanıldığından, paket yeni
  sürümde lisans bilgisi aynı kaldığı sürece önceki false positive / risk
  kabulü kararı sessizce devam eder; kullanıcı bu kararları yeni sürümde
  yeniden gözden geçirmez.
- P-09: sabit değerler git geçmişinde kalır (history rewrite kapsam dışı);
  repoda bulunmuş varsayılan değerler ifşa edilmiş kabul edilir ve kullanıcı
  tarafından yenilenir. Yenilenmezse geçmişte görünen değerler geçerliliğini
  korur.
- P-09 / AC-P09-5: veritabanında daha önce şifresiz (düz metin) saklanmış
  token'lar varsa, bu düzeltme sonrası bu projelerin taramaları `failed`
  olur. Yerel kurulum sıfırdan başladığı için bu kabul edilmiş bir
  sonuçtur (D-14); bu tür bir veri bulunursa token yeniden girilmelidir.
- Lisans doğruluğu genel ürün riskidir: araç paketin beyan ettiği lisansa
  güvenir, pakete gömülü farklı lisanslı dosyaları görmez. P-06 bu riski
  azaltır ama ortadan kaldırmaz.
