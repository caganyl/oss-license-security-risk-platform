# REQ-009: Şirket içi Azure DevOps Server (TFS) repoları ve .NET 10 desteği

## Değişiklik geçmişi

| Tarih | Revizyon | Değişiklik |
| --- | --- | --- |
| 2026-10-20 | r1 | İlk sürüm. Kararlar D-250…D-262. |
| 2026-10-20 | r2 | Kullanıcı onayı: "delete olmasın" — DELETE uç noktası ve arayüzde kaldırma kapsam dışı (D-262 güncellendi). |

## Amaç

Kullanıcı, şirketin kendi Azure DevOps Server'ındaki (`https://tfs.zorlu.com/…/_git/…`)
bir repoyu adresiyle taratmak istiyor; tarama her seferinde başarısız oluyor.
Ayrıca günlük kullanılan .NET 10 projelerinde asıl bağımlılık kaynağı
(`obj/project.assets.json`) okunamıyor. Bu REQ, ürünü kullanıcının kendi
ortamında **çalışır** hale getiren hata düzeltmelerini toplar:

- **P-29 — Repo erişim anahtarı (PAT).** Bir projeye, repo adresi için bir
  erişim anahtarı (Personal Access Token) tanımlanabilir. Anahtar şifreli
  saklanır, hiçbir yanıtta geri dönmez, yalnız o repo hostuna gönderilir.
- **P-30 — Windows kimliğiyle erişim (isteğe bağlı).** Yönetici `.env`'de
  açıkça listelediği şirket içi hostlar için, PAT tanımlı olmayan projelerde
  git'in oturum açmış Windows kullanıcısının kimliğini (Negotiate/NTLM ve
  Git Credential Manager) kullanmasına izin verebilir.
- **P-31 — Varsayılan dal ve anlaşılır klon hataları.** Dal belirtilmeyen
  taramalar reponun kendi varsayılan dalını klonlar (`main` varsayılmaz).
  Kimlik doğrulama, dal bulunamaması, sertifika ve bağlantı hataları
  kullanıcıya ne yapması gerektiğini söyleyen bir mesajla gösterilir.
- **P-32 — .NET 10 `project.assets.json` sürüm 4.** Ayrıştırıcı sürüm 3 ve 4'ü
  okur.

Kaynak: Kullanıcı talimatı (2026-10-20): "kendi azure devopsumuzdan link
gönderiyorum algılamıyor"; TFS kimlik doğrulama yolu sorusuna yanıt "İkisi de
olsun"; sıralama sorusuna yanıt "sırayla hepsi" (önce hatalar, ardından
UI/rapor revizyonu ayrı REQ).

Kullanıcı / paydaş: Aracı kendi Windows bilgisayarında çalıştıran geliştirici
(proje sahibi) ve şirket içi yazılım ekibi.

## Problem

Repo üzerinde doğrulanan durum (branch `main`, `85f2d8c`; yerel geliştirme
veritabanındaki gerçek tarama kayıtları):

1. TFS adresiyle oluşturulan projelerin taramaları
   `fatal: could not read Username for 'https://tfs.zorlu.com': terminal prompts disabled`
   ile `failed` oluyor. Klon süreci bilerek kullanıcının git ayarlarından ve
   kimlik deposundan yalıtılmıştır (REQ-002 N-1, ADR-002 Ek E1). Tek kimlik
   kaynağı `integrations.access_token_enc`'dir; ancak bu kaydı oluşturan hiçbir
   API veya arayüz yoktur ve `POST /api/scans` taramayı hiçbir entegrasyona
   bağlamaz. Sonuç: kimlik doğrulama isteyen **hiçbir** https repo taranamaz.
2. `POST /api/scans` gövdesinde `ref` yoksa `'main'` yazılır. Varsayılan dalı
   `master`/`develop` olan repolarda klon, kimlik sorunu çözülse bile
   "Remote branch main not found" ile düşer.
3. Klon hatası kullanıcıya ham git çıktısı olarak gösterilir; kullanıcı ne
   yapması gerektiğini anlayamaz.
4. .NET 10 SDK `project.assets.json` dosyasını `"version": 4` ile yazar.
   `src/scanner/parsers/nugetAssets.ts` yalnız `3` kabul eder; gerçek .NET 10
   projelerinde her `obj/project.assets.json` için "Desteklenmeyen
   project.assets.json sürümü." uyarısı çıkar ve kesin sürümler + geçişli
   bağımlılıklar kaybolur. Sürüm 4'te ayrıştırıcının okuduğu alanlar
   (`libraries.*.type`, `libraries.*.sha512`,
   `project.frameworks.*.dependencies.*.version`) sürüm 3 ile aynıdır
   (gerçek dosyada doğrulandı).

## Kapsam

1. `PUT /api/projects/{id}/repo-credential` (gövde `{ token }`); token
   yalnız yeni bir PUT ile değiştirilir, silme uç noktası yoktur. Proje başına en çok bir etkin
   entegrasyon kaydı; anahtar AES-256-GCM ile şifrelenir (mevcut
   `ENCRYPTION_KEY` düzeni).
2. Proje listesinde `has_repo_credential` (boolean). Anahtar hiçbir yanıtta,
   denetim kaydında veya hata metninde yer almaz.
3. `POST /api/scans` (dependency) projenin etkin entegrasyonunu taramaya
   bağlar (`integration_id`).
4. `GIT_WINDOWS_AUTH_HOSTS` yapılandırması ve klon ortamında yalnız bu hostlar
   için `http.<origin>.emptyAuth=true` + `credential.<origin>.helper=manager`.
5. Dal belirtilmeyen taramada `ref = NULL`; klon `--branch` olmadan reponun
   varsayılan dalını alır.
6. Klon hatalarının sınıflandırılması ve yol gösteren mesaj.
7. `project.assets.json` sürüm 3 ve 4.
8. Arayüz: proje oluşturma modalında ve proje satırında "Repo access token"
   alanı/düğmesi, anahtarın tanımlı olup olmadığının gösterimi, kısa açıklama
   metni.
9. README ve `.env.example` güncellemesi; handoff; güvenlik incelemesi.

## Kapsam Dışı

- Arayüzün Türkçeleştirilmesi, raporların yeniden tasarımı, ekran içi
  açıklamaların genel revizyonu → **REQ-010** (sıradaki iş).
- Webhook, PR taraması, entegrasyon başına birden çok repo, SSH ile klon.
- PAT'in TFS'e karşı önceden doğrulanması (anahtar kaydedilirken ağ isteği
  atılmaz; ilk taramada belli olur).
- Kullanıcının makinesine Git Credential Manager kurulumu (Git for Windows
  ile birlikte gelir).
- REQ-003 worker yarışı (D-203) — ayrı hata REQ'i olarak açık kalır.

## Acceptance Criteria

### Genel

- **AC-G-1:** Mevcut davranış korunur: entegrasyonu olmayan, `GIT_WINDOWS_AUTH_HOSTS`
  boş bir kurulumda yerel klasör ve açık (public) https repo taramaları
  bugünkü gibi çalışır.
- **AC-G-2:** Lint, typecheck ve tam test paketi yeşil.

### P-29 — Repo erişim anahtarı

- **AC-P29-1:** `PUT /api/projects/{id}/repo-credential` `integrations:write`
  yetkisi ister; bu yetkisi olmayan rol 403 alır. Çerezle yapılan çağrı
  `sameOrigin` korumasından geçer.
- **AC-P29-2:** Gövde tam olarak `{ "token": string }` olmalı; token 1…1024
  karakter, boşluk/kontrol karakteri içermez. Aksi 400 `invalid_token`.
- **AC-P29-3:** Projenin `repo_url`'i https değilse (yerel klasör veya boş)
  400 `repo_credential_not_applicable`. Proje yoksa 404.
- **AC-P29-4:** Başarılı çağrı projenin etkin entegrasyonunu oluşturur veya
  günceller. `provider` repo adresinden türetilir:
  - `dev.azure.com`, `*.visualstudio.com` veya yolunda `/_git/` geçen
    adres → `azure_devops`;
  - hostunda `gitlab` geçen → `gitlab`;
  - `bitbucket.org` → `bitbucket`;
  - diğer her şey → `github`.

  `repo_url` = projenin `repo_url`'i, `access_token_enc` = şifreli token.
  Yanıt 200 `{ data: { has_repo_credential: true, provider } }`; token
  yanıtta yoktur.
- **AC-P29-5:** `DELETE /api/projects/{id}/repo-credential` yoktur (kullanıcı
  kararı); token yalnız PUT ile değiştirilir.
- **AC-P29-6:** `GET /api/projects` her proje için `has_repo_credential`
  döndürür; `access_token_enc` veya token hiçbir yanıtta yoktur.
- **AC-P29-7:** Her PUT bir denetim kaydı yazar; `old_data`/`new_data`
  token veya şifreli değer içermez (yalnız `provider`, `has_repo_credential`).
- **AC-P29-8:** Dependency taraması oluşturulurken projenin etkin
  entegrasyonu varsa ve entegrasyonun `repo_url`'i projeninkine eşitse
  `scans.integration_id` doldurulur. Worker mevcut yoldan token'ı çözer ve
  klona host kapsamlı başlık olarak verir (ADR-002 karar 3).
- **AC-P29-9:** Azure DevOps (bulut ve sunucu) için Basic kullanıcı adı boş
  dizedir (`:PAT`); bu kural `dev.azure.com`, `*.visualstudio.com` ve yolunda
  `/_git/` geçen her adres için uygulanır.
- **AC-P29-10:** Projenin `repo_url`'i entegrasyonunkinden farklıysa
  entegrasyon taramaya bağlanmaz; token başka hosta gitmez.

### P-30 — Windows kimliğiyle erişim

- **AC-P30-1:** `GIT_WINDOWS_AUTH_HOSTS` virgül ve/veya boşlukla ayrılmış tam
  host adları alır (joker, port, şema yok); büyük/küçük harf duyarsız. Geçersiz
  girdi başlangıçta anlaşılır bir hatayla süreci durdurur. Boş = kapalı.
- **AC-P30-2:** Klon URL'sinin hostu listedeyse **ve** taramada token yoksa,
  klon ortamına yalnız şu iki ayar `GIT_CONFIG_*` ile eklenir:
  `http.https://<host>[:port]/.emptyAuth=true` ve
  `credential.https://<host>[:port]/.helper=manager`. Başka host için
  eklenmez; token varsa eklenmez (PAT önceliklidir).
- **AC-P30-3:** Bu modda Git Credential Manager'ın çalışması için gereken
  kullanıcı ortam değişkenleri (`USERPROFILE`, `APPDATA`, `LOCALAPPDATA`,
  `USERNAME`, `USERDOMAIN`) yalnız bu durumda geçirilir; `GIT_TERMINAL_PROMPT=0`
  ve `GCM_INTERACTIVE=never` korunur (ekran açılmaz, takılmaz).
- **AC-P30-4:** Diğer tüm yalıtım ayarları (`GIT_CONFIG_NOSYSTEM`, yalıtılmış
  `GIT_CONFIG_GLOBAL`, `HOME`, kancalar) her modda aynıdır.

### P-31 — Varsayılan dal ve anlaşılır hatalar

- **AC-P31-1:** `POST /api/scans` gövdesinde `ref` yoksa veya boşsa
  `scans.ref = NULL` yazılır; worker `--branch` vermeden klonlar. PUT ile
  oluşturulan entegrasyonun `default_branch` sütunu taramaya ref olarak
  verilmez (D-255).
- **AC-P31-2:** Klon hatası aşağıdaki sınıflara ayrılır ve taramanın
  `error_message`'ı sınıfa özgü, yol gösteren bir İngilizce cümleyle başlar;
  ardından temizlenmiş git ayrıntısı gelir:
  - kimlik doğrulama (`could not read Username`, `Authentication failed`,
    `401`, `403`): "Repository requires authentication: add a repo access
    token to the project, or list the host in GIT_WINDOWS_AUTH_HOSTS."
  - dal yok (`Remote branch … not found`): "Branch not found in the repository."
  - repo yok (`Repository not found`, `404`): "Repository not found or no access."
  - sertifika (`SSL certificate problem`, `schannel`): "TLS certificate of the git server is not trusted."
  - bağlantı (`Could not resolve host`, `Failed to connect`, `timed out`):
    "Git server could not be reached."
- **AC-P31-3:** Kimlik doğrulama, dal yok, repo yok ve sertifika sınıfları
  kalıcıdır (yeniden denenmez); bağlantı sınıfı ve sınıflandırılmamış
  hatalar mevcut yeniden deneme kuralına tabidir.
- **AC-P31-4:** Hata metinleri token'ı (ham ve base64) ve çalışma alanı yolunu
  içermez (mevcut temizleme korunur).

### P-32 — .NET 10

- **AC-P32-1:** `project.assets.json` `version` 3 veya 4 ise okunur; diğer
  değerler mevcut "Desteklenmeyen project.assets.json sürümü." hatasıyla
  reddedilir.
- **AC-P32-2:** Sürüm 4 fixture'ı ile doğrudan/geçişli ayrımı, kesin sürümler
  ve sha512 kayıtları sürüm 3 ile aynı kurallarla üretilir.

### Arayüz

- **AC-UI-1:** Proje oluşturma modalında, repo adresi https ise görünen,
  isteğe bağlı "Repo access token (PAT)" parola alanı ve kısa açıklama: ne
  olduğu, Azure DevOps'ta nereden alınacağı (Code → Read yetkisi yeterli).
  Proje oluşturulduktan sonra token ayrı PUT çağrısıyla kaydedilir.
- **AC-UI-2:** Proje satırında https repolar için "Token" düğmesi: tanımlıysa
  "Token set" etiketi ile değiştir; değilse ekle. Kaldırma seçeneği yoktur. Token değeri arayüzde
  hiçbir zaman geri gösterilmez.
- **AC-UI-3:** Başarısız taramanın hata mesajı tarama satırında okunur
  biçimde görünür.

## Riskler

- **R-1:** Windows kimliği modu, listelenen hostlara kullanıcının kimliğini
  gönderir. Azaltım: yalnız yöneticinin açıkça listelediği tam host adları;
  joker yok; varsayılan kapalı; PAT önceliklidir.
- **R-2:** TFS'in PAT'i Basic auth ile kabul etmemesi (IIS ayarı). Azaltım:
  anlaşılır kimlik hatası; Windows kimliği modu alternatif.
- **R-3:** Gerçek TFS'e karşı uçtan uca doğrulama geliştirme oturumundan
  yapılamıyor (kimlik bilgisi yok). Kullanıcı elle doğrulayacak (handoff).

## Notlar

### Kararlar

- **D-250:** Yeni tablo yerine mevcut `integrations` tablosu kullanılır; proje
  başına tek etkin kayıt (uygulama düzeyinde zorlanır).
- **D-251:** Uç nokta proje altında tekil kaynak:
  `/api/projects/{id}/repo-credential` (yalnız PUT). Ayrı entegrasyon CRUD'u
  kapsam dışıdır.
- **D-252:** Yetki `integrations:write` (rol matrisinde yalnız admin).
- **D-253:** URL yolunda `/_git/` geçen her adres `azure_devops` sayılır
  (şirket içi TFS'in host adı tahmin edilemez); Basic kullanıcı adı buna göre
  boş dizedir.
- **D-254:** Windows kimliği modu host listesiyle açılır
  (`GIT_WINDOWS_AUTH_HOSTS`); ADR-002 Ek E1'e kontrollü istisna (ADR-011).
- **D-255:** Dal belirtilmeyen tarama `ref = NULL`; varsayılan dal tahmini
  yapılmaz, git uzak HEAD'i izler.
- **D-256:** Hata sınıflandırması klon katmanında yapılır, mesaj İngilizcedir
  (API dili); Türkçeleştirme REQ-010'da arayüz katmanında.
- **D-257:** Kalıcı hata sınıfları `NonRetryableScanError` olarak işaretlenir.
- **D-258:** Token kaydedilirken TFS'e doğrulama isteği atılmaz.
- **D-259:** `project.assets.json` için kabul edilen sürümler {3, 4}.
- **D-260:** Arayüz metinleri bu REQ'te mevcut arayüz diliyle (İngilizce)
  yazılır; REQ-010 tümünü Türkçeleştirir.
- **D-261:** Token üst sınırı 1024 karakter.
- **D-262:** Silme uç noktası yok (kullanıcı, 2026-10-20: "delete olmasın").
  Token yalnız PUT ile değiştirilir; entegrasyon kaydı hiç silinmez.
